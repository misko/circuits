## 2. BLOCKING — `M-REL` parses **0 of 63** MANIFEST rows, and the M-COVER backstop written for exactly this is defeated by a substring

MEASURED, with a red control.

`policy_audit.py` M-REL verifies the sha256 table with one regex that admits two
table layouts (`policy_audit.py:1643-1646`): `'  <path>  <hash>'` and
sha256sum's `'<hash>  <path>'`. **This archive ships a THIRD layout** —
`<hash>  <size>  <path>`:

```
9c0104bb7bcb0d07fbb8edcb328cccc611f9d0f9b6781c297147a40fbf564932      406941  3d/pluto_rx2_8way_v2.step
```

Running that exact regex over the shipped `MANIFEST.txt`: **0 entries matched**
against 63 real hash rows.

The gate has a backstop for precisely this — the comment above it records
usb-hub-3s-v3 matching "ZERO of 76 entries … M-REL reported 'provenance +
hashes verify' on that board for all ten of its releases while verifying
nothing", and concludes "a denominator that silently goes to zero is the
M-COVER shape, so … an empty table is now a FAIL in its own right". **That
backstop does not fire here.** It is guarded by
`if _hashed == 0 and _n_files and "sha256:" in mt` — a literal-substring key.
This MANIFEST's banner reads `ARCHIVE CONTENTS — sha256, and BIJECTIVE …`.
`"sha256:" in mt` is **False**, MEASURED. The guard is skipped and the gate
grades PASS.

**End-to-end proof on a real release-shaped fixture** (scratch copy, own git
repo, staging tree placed at `07_releases/v1.0-2026-07-31/`):

| test | archive state | MANIFEST layout | M-REL result |
|---|---|---|---|
| A | **`verification/stock_check.txt` DELETED** (a manifested row) | shipped 3-column | **PASS** — "provenance + hashes verify" |
| C2 | same file deleted, nothing else changed | rewritten to 2-column `sha256sum` | **FAIL: missing hashed file verification/stock_check.txt** |
| D | one file's bytes changed | 2-column | **FAIL: sha256 mismatch verification/stock_check.txt** |

A and C2 differ in **one thing**: the column layout. So the code path that
catches the cooksense-v1.7 shape (#53 — a MANIFEST row whose file is absent)
exists, works, and **cannot see this release**.

Fleet context, MEASURED across all 34 sealed release manifests: every other
release matches near-fully (e.g. cooksense v1.7 122/122, central-v2 v1.7 73/73);
the outlier is usb-hub-3s-v3 v1.2 at **11/35**, which is a second, smaller
instance of the same partial-coverage blindness and is worth its own look.
pluto would be the first at **0/63**.

**Why this blocks rather than waits.** The archive really is bijective — I
verified all 63 rows myself. But sealing writes an immutable directory whose
integrity claim would then rest on one agent's one-off script instead of a gate,
and the repair path afterwards is a superseding version. Two ways to close it,
either acceptable: emit the 2-column layout the gate reads, or widen the gate's
regex to the 3-column form **and** replace the `"sha256:"` substring guard with
a structural one (count of `[0-9a-f]{64}` lines vs matched entries). If the gate
is touched, the red control above is the known-bad fixture, and it is already
measured RED against the pre-fix code.
