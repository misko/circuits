RELEASE-FRESHNESS EXCEPTIONS — v1.12-2026-07-28
================================================

`release_freshness_check.py` flags an artifact that is sha256-IDENTICAL to an
earlier release's, because "a changed board must not ship an earlier release's
generated output". That rule is right, and it has TWO legitimate exceptions on
this release. Each is an IDENTITY THAT SHOULD BE ASSERTED, not excused: a
CHANGED file would mean something moved that this release does not claim to have
moved.

There is no supersede MODE that fits this release. The modes are docs-only,
bom-only, cpl-only, legible-bom, sourcing and value-change; this is the
complement of all six — the COPPER changed and the BOM did not. So the two
exceptions are declared here with their measurements rather than mode-asserted.
That is weaker than a mode, and it is named as weaker. A `--copper-only-supersede`
mode (assert: bom.csv byte-identical, .kicad_sch byte-identical, netlist parity 0,
board md5 CHANGED, gerbers CHANGED) is filed as a follow-up and deliberately not
built inside a footprint fix.

Both exceptions are passed as `--allow-identical <relpath>`. There are TWO of
them. v1.11 shipped SEVEN.

-------------------------------------------------------------------------------
EXCEPTION 1 — pdf/schematic.pdf identical to v1.9 / v1.10 / v1.11
-------------------------------------------------------------------------------
sha256 db01cea80d1af9d2309a5494f9b07274188346529f1077323bed782c21fee61d

WHY IT IS IDENTICAL BY DESIGN: the schematic did not change, and cannot have.
This release edits ONE footprint's copper geometry. Measured, not argued:

  1. `04_kicad/usb_hub_3s_v2.kicad_sch` is BYTE-IDENTICAL to v1.11's sealed copy
     and to git HEAD (`git diff --stat` empty; sha256
     f007c55a3fe0a64efb6b864ffc3c83b693fd2ef57d8d5bd500ede30e60f664b2 on all
     three of 04_kicad/, v1.11/source/ and v1.12/source/).
  2. Netlist parity is 0 — 122 components, 73 nets, 372 nodes identical to
     v1.11's sealed .net, by two independent tools (verification/parity.md).
  3. The DRC gate's --schematic-parity leg reads 0.
  4. A land pattern is not drawn on a schematic. The .kicad_sch names the
     footprint (`usb_hub_3s:TYPE-C-31-M-12_EdgeTrim`, 1 occurrence) and carries
     none of its geometry.

  The shipped PDF is tscircuit's own render (ADR-0002), copied from
  03_tscircuit/build/schematic.pdf, whose sha256 matches. A CHANGED schematic.pdf
  on this release would be the signature of an unintended electrical edit.

-------------------------------------------------------------------------------
EXCEPTION 2 — fab/bom.csv identical to v1.11
-------------------------------------------------------------------------------
sha256 1dfc50426d09cb6a76e7a5970d4035b36633d6f2b8a314838df9136563038963

WHY IT IS IDENTICAL BY DESIGN, and this is the identity that most needs
asserting: NO PART CHANGED. This release moves copper under J5; it does not
buy a different J5, a different anything. The BOM is 46 lines, the same 46
lines, in the same order, with the same LCSC codes, MPNs and Comments.

  Corroborated from the other side: `fab/cpl.csv` is NOT identical — it differs
  in exactly ONE row (J5, Mid Y -107.502 -> -107.705), which is precisely the
  shape a pad-geometry fix should produce. A BOM that had moved here would mean
  the fix had reached the parts list, which it must not.

  Re-derived, not copied: this bom.csv was regenerated by export_jlc_package.py
  from the REBUILT board, and came out byte-identical. It is not v1.11's file.
