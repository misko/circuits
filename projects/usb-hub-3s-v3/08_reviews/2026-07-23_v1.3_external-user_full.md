Detailed v1.3 review
Verdict
Do not order the current v1.3 directory yet.
The main v1.3 changes are good: R12 is now a verified 4.12 kΩ part, D5 is now a confirmed unidirectional TVS, the output-drop calculation uses the real Q6+F2 path, the stale fabrication PDFs were regenerated, and F1/SW1 were removed from automated placement.
However, v1.3 is presently a staged, blocked release, not a completed seal. The live status says gate ii is complete but gate iii—the fresh independent red-team and final seal—is still pending. The latest commit also explicitly reports an unfixed R30 BOM-value mismatch.
My overall assessment:

1. v1.3 is not actually sealed
The release manifest presents v1.3 as completed and claims:
M-BOM PASS.
Policy audit with zero failures.
Fresh v1.3 red-team evidence added before seal.
But the repository's current status still says:
stage: v1.3-fix-gate-ii
state: blocked
gate iii fresh red-team and two-commit seal remain next.
More importantly, after the current manifest was produced, the new semantic BOM checker found R30 to be wrong. The latest commit states this is not yet fixed and must be folded into gate iii before seal.
Therefore, treat 07_releases/v1.3-2026-07-23/ as a work-in-progress release candidate, regardless of the directory name or manifest wording.
2. R30 is still the wrong physical resistor
The design intends:
R30 = 100 kΩ
PMID ── R30 ── Q6 gate
The source clearly defines R30 as 100 kΩ and explains that it pulls Q6's gate to its source when Q7 is off.
But the fabrication BOM contains:
100kΩ,R30,...,C2933195
C2933195 is actually FRC0603F3091TS, 3.09 kΩ ±1%, not 100 kΩ. The official JLC entry confirms that catalog value.
Electrical consequence
Unlike the v1.2 R12 error, this probably would not cause immediate board failure.
When the board is on:
I R30 ≈ 3090 5.35 =1.73 mA
R30 dissipates approximately:
P≈ 3090 5.35 2 =9.3 mW
Q7 must continuously sink that roughly 1.7 mA. That is not a difficult load for a BSS138, and Q6 should still receive a strong negative gate voltage.
When the board is off, R30 still pulls Q6's gate to its source, so the reverse-blocking mechanism remains conceptually correct.
Thus:
Release/process severity: blocker, because the BOM contradicts the design and the release gate is known to fail.
Likely electrical severity: modest; the circuit probably still functions.
Side effect: approximately 1.7 mA of unnecessary on-state current instead of about 53 µA with 100 kΩ.
The simplest fix is to assign R30 the same verified 100 kΩ code already used by R1, R8, and R17: C25803.
Alternatively, the designers could intentionally adopt 3.09 kΩ, update the source and documentation, and verify Q7 dissipation and sequencing. There is little reason to do so; 100 kΩ is adequate and avoids unnecessary draw.
3. The feedback-divider tolerance analysis is incomplete
v1.3 correctly uses:
R12 = 4.12 kΩ ±0.1%, C2984354.
R13 = 1.21 kΩ, C5126242.
LM5116 reference = 1.215 V, ±1.5%.
R12 is now correctly cataloged as 4.12 kΩ ±0.1%.
However, C5126242 is a 1.21 kΩ ±1% resistor—not 0.1%.
The power-tree calculation states:
nominal 5VC = 5.352 V;
minimum = 5.27 V;
maximum = 5.43 V.
Those figures appear to apply only the LM5116's ±1.5% reference tolerance, not the divider-resistor tolerances.
TI specifies the LM5116 reference as 1.215 V with 1.5% precision.
Including:
R12 ±0.1%;
R13 ±1%;
reference ±1.5%;
gives approximately:
V 5VC,min ≈5.227 V
V 5VC,max ≈5.479 V
Why that matters
Low-output corner
The project's modeled delivery path is 88 mΩ from 5VC through Q6, F2, PCB, connector, and cable.
At 5 A:
V drop ≈5×0.088=0.44 V
So the revised worst-case cable-end estimate is approximately:
5.227−0.44=4.787 V
That is still above Raspberry Pi's nominal 4.63 V undervoltage threshold, but the margin is thinner than the manifest claims. Raspberry Pi specifies low-voltage detection at 4.63 V ±5%, so cable-end validation remains essential.
High-output corner
At essentially zero load there is little Q6/F2 drop, so the USB-C receptacle could approach 5.48 V in the static worst case, before considering transient overshoot.
Raspberry Pi specifies a 5 V/5 A supply for Pi 5 and generally describes its supplies as 5.1 V.
I would not accept 5.48 V solely on paper without:
measuring no-load output on assembled boards;
measuring load-release overshoot;
specifying a firm maximum such as 5.45 or 5.50 V;
verifying that the real Pi and attached devices tolerate it.
Recommended correction
Use a 0.1% 1.21 kΩ resistor for R13, and ideally R4 as well. With both divider resistors at 0.1%, the approximate USB-C static range becomes:
5.264 V to 5.441 V
That more closely matches the existing documentation and reduces both undervoltage and overvoltage uncertainty.
The same issue applies to USB-A buck A: R3 is a precision 3.92 kΩ part, but R4 is the same 1% 1.21 kΩ lower resistor. Its true upper corner can slightly exceed the intended 5.25 V USB-A ceiling.
4. The header fallback instructions reverse ON and OFF
The source connects:
SW1 T1 → GND.
SW1 COM → ENKILL.
Grounding ENKILL disables both LM5116 converters.
Therefore:
COM–T1 shunted = OFF
shunt removed   = ON
But the v1.3 README says:
"COM-T1 shunted = ON; shunt removed = OFF"
That is reversed.
It is not likely to damage anything, but it could cause confusing commissioning and troubleshooting. Correct the README before the release is finalized.
There is also a minor F1 description error in the same table: it calls the fuse holder KH-AF90DIP-112, which is the USB-A connector family. The actual F1 BOM item is the Keystone-style mini-blade fuse holder C5249699.
5. F1 and SW1 remain in the PCBA BOM but are absent from the CPL
v1.3 deliberately excludes F1 and SW1 from position files and says they should be hand-soldered.
However, both remain in the assembly BOM:
SW1 = C2939728.
F1 = C5249699.
This may result in JLC showing unmatched BOM designators or asking for placement data. It is manageable in the order interface, but it is not a clean upload package.
I recommend producing two distinct BOMs:
PCBA BOM: only the 108 automatically placed components.
Complete purchasing/assembly BOM: includes F1, SW1, and the 10 A blade fuse.
At minimum, mark F1 and SW1 explicitly as DNP/not assembled during the JLC order review.
6. Fail-high protection remains best-effort—and v1.3 is honest about it
v1.3 does not add deterministic active overvoltage isolation. Its protection is still:
5VC → Q6 → F2 → VBUSC
                   │
                   D5
                   │
                  GND
D5 C113976 is now correctly identified as a unidirectional SMBJ6.0A, with:
6 V stand-off;
7.37 V breakdown;
10.3 V clamp;
600 W under a 10/1000 µs pulse;
58.3 A peak-pulse rating.
F2 is a 7 A-hold, 14 A-trip, 16 V PPTC; its catalog maximum trip time is approximately 2 seconds under the specified test condition.
Therefore, during a buck high-side short:
D5 may keep the connector around 8–10 V rather than 5 V.
F2 and/or the upstream blade fuse must open.
The Pi can be exposed to damaging voltage before that happens.
The TVS pulse rating does not guarantee survival of a sustained DC crowbar fault.
The README now states this accurately and no longer claims deterministic fail-high protection.
Given your intended 300 hours of supervised prototype operation, replaceable Pi, and extremely low intrinsic probability of this failure, accepting this residual risk is reasonable. It would not be acceptable for an unattended commercial deployment or valuable attached hardware.
7. The normal USB-C power calculation is plausible but requires the planned bench gate
The intended normal operating values are:
Local 5VC nominal: approximately 5.352 V.
Q6 maximum channel resistance: approximately 4.3 mΩ.
F2 cold maximum resistance: 18 mΩ; modeled hotter value around 31 mΩ.
Board + connector: approximately 8 mΩ.
Cable allowance: approximately 45 mΩ.
Total modeled path: approximately 88 mΩ.
With nominal 5VC:
V Pi ≈5.352−(5×0.088)=4.912 V
That should be adequate with the intended short, heavy cable. Raspberry Pi recommends a 5 V/5 A supply for Pi 5 when full peripheral power is needed.
But F2 is the least predictable element because its resistance rises with temperature. The README's mandatory test of the exact cable at 5 A is therefore appropriate.
I would tighten its pass criterion slightly:
Board connector VBUSC at 5 A: preferably ≥5.00 V.
Cable end at 5 A hot: preferably ≥4.80–4.85 V, not merely 4.75 V.
No undervoltage events during fast load transitions.
8. What v1.3 does well
The following are genuine improvements:
R12 is now the correct component. C2984354 is officially 4.12 kΩ ±0.1%.
D5 is now the correct directionality. C113976 is unidirectional and in the correct SMB package.
The feedback remains local to 5VC, avoiding v1.1's remote-sense runaway.
The output-loss model now uses Q6+F2, rather than the removed TPS26631 eFuse.
Artifact freshness was addressed. The assembly and layer PDF hashes are now different from previous releases.
SW1 is no longer trusted to automated placement despite the unresolved pitch.
The README clearly defines a pre-Pi qualification procedure.
The overvoltage limitation is now described honestly, rather than presenting the TVS+PPTC as guaranteed Pi protection.
Required actions before ordering
Mandatory release fixes
Change R30 to a real 100 kΩ part, preferably C25803, and bake the code into source.
Regenerate schematic, board, BOM, CPL, audit, twin and manifest after the R30 fix.
Rerun the new semantic BOM checker; archive its current output, not the old identity-only PASS.
Complete gate iii with a fresh v1.3 red-team review.
Correct the COM–T1 header ON/OFF instructions.
Correct the F1 holder description.
Decide whether F1/SW1 should be removed from the PCBA BOM entirely.
Strongly recommended design fix
Change R4 and R13 to verified 0.1% 1.21 kΩ parts, or explicitly include their ±1% tolerance in all output-voltage gates.
Add explicit maximum-voltage criteria to the scope tests:
5VC/VBUSC no-load maximum.
Load-release overshoot maximum.
Keep the current active-OVP escalation boundary: add deterministic isolation before using the system unattended or with expensive SDR/storage hardware.
Deployment tests
The README's Q1–Q5 sequence is good. I would add:
Verify R30 before power as well as R12.
Measure 5VC and VBUSC at zero load before connecting anything.
Verify SW1/header logic with a continuity meter.
Capture VBUSC during a 5 A→0 A load release.
Check vcgencmd get_throttled throughout the final Pi stress test.
Final disposition
Current v1.3 repository state: DO NOT ORDER.
After R30 is corrected, divider tolerances are addressed, documentation is fixed, and gate iii is completed: v1.3 should be a credible supervised 300-hour prototype board.
It will still not provide guaranteed protection against a buck high-side short, but for your short operating duration and accepted replaceable-Pi risk, that residual failure mode is probably reasonable.
