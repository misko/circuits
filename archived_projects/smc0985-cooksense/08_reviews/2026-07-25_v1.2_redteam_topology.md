## Floating-input hunt

I traced every net reaching a logic input or a MOSFET gate. **No net floats to a
level that leaves an actuator energised in steady state.** That result is
structural, not luck: `SR_OE_N = NAND(MCU_RELAY_ENABLE, WD_OK)` shares both of
its terms with `KEY_RELAY_ALLOWED`, so the coil rail can never be up while the
shift register is tri-stated. This is good design and I want it on the record.

Nets that *do* float, with their (nil) actuator consequence — collected as P2-1:
`PRESS_REQ` {U_SR1.7, U_ONESHOT.2 — **no pull at all**}, `DECU_A/B/C`,
`DECD_A/B` (covered by the G1 pulldowns), `KEY_DATA`, `KEY_CLOCK`, `KEY_LATCH`,
`ADC_CS_N`, `TC_CS_N`, `SPI_SCLK/MOSI/MISO`.

The real failures in this class are two external inputs that are pulled to the
**permissive** level rather than floating — P1-2 (door) and P1-3 (thermistor).
Every other external safety input (ESTOP_RAW, MODE_RAW, COIL_EN, WD_PET) is
pulled to the restrictive level.

## Findings

### P0-1 The hardware watchdog can be silently disabled by a high-impedance host pin — WDI hold resistor is 100 kΩ where TI specifies 1 kΩ

evidence: `WD_PET` = {`J_PI.11` (GPIO17), `R_WDPETPD` (**100 kΩ**, other end
GND), `U_WD.4` WDI}. TPS3823 datasheet SLVS165O §7.3.4, verbatim: *"The watchdog
timer can be disabled by disconnecting the WDI pin from the system. If the WDI
pin detects a high-impedance state, the TPS3820, TPS3823, TPS3824, or TPS3828
generates internal WDI pulse to make sure that RESET does not assert. **If this
behavior is not desired, place a 1 kΩ resistor from WDI to ground.**"*
Corroborating electrical spec (SLVS165O §6.5): WDI I_IH and I_IL are both
**140/190 µA** — 190 µA across 100 kΩ demands 19 V, i.e. the internal network
dominates the external resistor by ~20x. The block diagram (§7.2) shows the
auto-reset oscillator driving WDI through 40 kΩ; against 100 kΩ the pin reaches
3.3 × 100/140 = **2.36 V** vs V_IH = 0.7·VDD = **2.31 V** — a valid HIGH, so the
transition detector self-pets. The board is 100x above the datasheet-prescribed
value.

consequence: whenever GPIO17 is high-impedance the supervisor pets itself and
`WD_OK` never falls. The failure is **silent and self-concealing** — `TP_WDOK`
reads healthy with nothing connected. This defeats brief §3 ("heartbeat loss
drops relay power"), C10 ("Pi crash/network loss: watchdog disables relays") and
the whole "de-energise in hardware without firmware cooperation" premise. The
exposure: a host process that releases the heartbeat line back to input (the
normal Linux gpiod behaviour on process death) while a separate handle keeps
GPIO22/23 driven high leaves the **key-relay rail energised and the external
contactor closed with no supervisor at all**. It also means the board cannot
distinguish "host never started" from "host healthy". The full-unplug case is
still safe, but only because HOST_AUTH/MCU_RELAY_ENABLE have their own
pulldowns — the watchdog itself contributes nothing.

fix: `R_WDPETPD` 100 kΩ → **1 kΩ** (TI's number; ≤4.7 kΩ satisfies V_IL =
0.3·VDD = 0.99 V against the 190 µA max). Cost to the Pi: 3.3 mA when driving
high — trivial. One-minute bench proof: set GPIO17 to input and scope
`TP_WDOK`; it must go low within 2.5 s.

This is a single resistor value and it blocks the order.

### P1-1 Watchdog window is 0.9–2.5 s; the brief specifies 300–500 ms

evidence: SLVS165O §6.7, t_tout for TPS3823 = **0.9 / 1.6 / 2.5 s**. Brief §3:
"Watchdog 300-500ms". The part's own `part.yaml` gotcha already records the gap
and says the fast window "is the SN74LVC1G123 one-shot" — but v1.2 swapped that
part out for the CD74HC221, and in the netlist `U_ONESHOT` section 2 is
hard-disabled (`2A_N`=3V3, `2B`=GND, `2R_N`=GND, `2Q`/`2Q_N` unconnected).
**There is no fast watchdog on this board.**

consequence: worst-case 2.5 s of unsupervised operation after heartbeat loss, 5x
the specified window. Mitigated in that PRESS is independently bounded to
≈357 ms by the '221, so the OEM keypad cannot be held down; the exposure is the
contactor staying closed for up to 2.8 s (2.5 s + t_d). Accept explicitly with
that reasoning, or add a second supervisor.

### P1-2 The door interlock is inert — R_DOORPU is a pull-UP where every other external safety input uses a pull-DOWN

evidence: `DOOR_RAW` = {`J_DOOR.2`, `J_DOOR.4`, `R_DOORPU` 10 kΩ **to 3V3**,
`D_DOOR`, `U_SCHM.11`}. `U_SCHM` is a double inversion (11→10 `DOOR_NI`, 13→12
`DOOR_OK`), so `DOOR_OK = DOOR_RAW`. Compare `ESTOP_RAW` = {`J_ESTOP.2`,
`R_ESTOPPD` 10 kΩ **to GND**, …} and `MODE_RAW` = {`J_MODE.2`, `R_MODEPD` 10 kΩ
**to GND**, …}. All three connectors share the same pin convention (pin 1 = 3V3,
pin 5 = GND) — confirmed in `cooksense.tsx` lines 420–442. Note also that
`J_DOOR.2` and `J_DOOR.4` are the **same net**, so a two-terminal reed wired
pin2–pin4 is a no-op.

consequence: with the E-stop-style harness (3V3 → reed → signal) the pull-up
already holds `DOOR_RAW` high, so **the reed has no effect and `DOOR_OK` is
permanently 1** — the door abort silently never happens. With the
pull-up-consistent harness (signal → reed → GND) and a normal magnet-closes
reed, `DOOR_OK = 0` whenever the door is *closed*, which holds `OS_CLR_N` low
and means **K_PRESS can never fire** — non-functional. Either way, brief §3
("open ⇒ abort sequence, release PRESS+selectors, no new START") is not met. And
in the built configuration an unplugged or broken door cable reads *permissive*,
the opposite of every other input on this board. Note the OEM door interlock is
untouched and still cuts the magnetron, which is why this is P1 and not P0.

order-time mitigation (if you ship): specify a **Form-B** reed (opens with the
magnet present) wired `J_DOOR.2 → J_DOOR.3(GND)`. Then closed door → reed open →
pull-up → DOOR_OK=1; open door → reed closed to GND → DOOR_OK=0. Correct
polarity, but still fail-permissive on cable break — document that. Proper fix
next rev: move `R_DOORPU` to GND and use the E-stop harness. Additionally, gate
the selectors and/or the contactor on DOOR_OK, not just the one-shot reset.

### P1-3 The hardware over-temperature inhibit is fail-permissive on an open or disconnected camera thermistor

evidence: `TH_CAM_A` = {`J_THERM_A.5`, `R_REF0` 10 kΩ **to 3V3_ANALOG**,
`R_SER0`, `R_HYS1`, `U_COMP.3`}; the NTC lives on the external thermal head.
Head unplugged / NTC open / wire broken → node pulled to **3.3 V**, far above the
0.4231 V threshold → `TEMP_OK` stays HIGH = "temperature fine". Second,
independent problem: LM393 V_ICR = 0 to VCC−2 V; with VCC = 5V_PROTECTED ≈
4.93 V that ceiling is **2.93 V**, so at 3.3 V the comparison is outside the
specified common-mode range and the output state is **unspecified**. The LM393
`part.yaml` gotcha asserts *"a thermistor divider referenced to 3V3_ANALOG is
safe"* — true only while a thermistor is fitted; the netlist violates its own
stated condition in the open-circuit case.

consequence: a single unplugged JST-GH cable removes the only
firmware-independent over-temperature protection, silently, and simultaneously
removes it from the fault-latch SET term and the contactor gate
(`U_FAULTAND.6`, `U_CAND1.6`). Brief §3 demands a comparator inhibit
"independently of Pi/LLM", and C14 demands open/short detection — a shorted NTC
trips safe, an open one does not. The board *has* the ingredients for detection
(the same node reaches MCP3208 CH0/CH3 through R_SER0/R_SER3), but that is a
host-software check, i.e. exactly the dependency the hardware inhibit exists to
remove.

fix: add a bottom-side resistor (e.g. 200 kΩ NTC-parallel or a series element at
the connector) so an open head produces an in-range "hot" reading, or run the
comparator from 3V3 so the CM range covers the full swing and add a window
comparator. Order-time mitigation: a mandatory bring-up step that unplugs each
head and proves `TP_TEMPOK` goes low — if it does not, the head cable is a
single point of failure.

### P1-4 The 595 storage register is undefined at the moment SR_OE_N releases — arbitrary key press at enable

evidence: `SR_OE_N = NAND(MCU_RELAY_ENABLE, WD_OK)` (U_OENAND) — it is **not**
gated by `KEY_RELAY_ALLOWED` or `FAULT_LATCH_CLEAR`. The 74HC595 storage
(output) register has no reset: `SRCLR_N` (`KEY_RESET_N`, R_KRSTPD 100 kΩ↓)
clears only the *shift* stages; the storage register only updates on RCLK. So
when the Pi asserts MCU_RELAY_ENABLE, `SR_OE_N` falls and `DECU_A/B/C`,
`DECU_G1_RAW`, `DECD_A/B`, `DECD_G1_RAW`, `PRESS_REQ` all go live with
power-on-undefined content — at the same instant `KEY_RELAY_ALLOWED` brings the
coil rail up (both are functions of MCU_RELAY_ENABLE). `PRESS_REQ` has **no pull
resistor** (net = {U_SR1.7, U_ONESHOT.2} only), so its Hi-Z→1 transition is a
valid rising edge into the '221's Schmitt B input.

consequence: if the undefined pattern happens to have QD=1 (U decoder enabled),
QG=1 (D decoder enabled) and QH=1, a **random one of the 18 OEM keys is pressed
for ≈357 ms at the moment cooking authorisation is granted**. The only
mitigation is procedural (host must pulse SRCLR_N and RCLK to load zeros before
raising MCU_RELAY_ENABLE), which contradicts D1's "all enforcement moves to
hardware". Note the user waived the rogue-valid-keypress concern in T6, which is
why this is P1.

fix: gate `SR_OE_N` with a term that lags the rail (e.g. AND in
`FAULT_LATCH_CLEAR`), or add a hardware POR that pulses RCLK once with SRCLR_N
asserted. Add a 100 kΩ pulldown on `PRESS_REQ` regardless. Order-time
mitigation: make "SRCLR_N low + RCLK pulse, then verify TP_USEL/TP_DSEL open,
before MCU_RELAY_ENABLE" a mandatory sequence in the host driver and in the
G4/G5 procedure.

### P1-5 eFuse overvoltage cutoff is set at ~9.2 V, not the intended ~5.7 V

evidence: `EF_OVLO` = {`R_OVT` 100 kΩ from `5V_RPP`, `R_OVB` 15 kΩ to GND,
`U_EFUSE.2` EN/OVLO}. SLVSE57C §6.5: V_OVLO(R) = **1.13 / 1.20 / 1.27 V**. Trip
point = 1.20 × (115/15) = **9.20 V** (8.66–9.74 V over tolerance). The part's own
`part.yaml` gotcha states the design intent: *"For a 5 V nominal rail, set the
OVLO divider for ~5.5-6 V cutoff."* For 5.7 V you need ≈100 k/26.7 k.

consequence: the device does still enable at 5 V (0.652 V < V_OVLO(F) 1.03 V), so
the board powers up — this is not a P0. But a 7.5–9.2 V source on the Micro-Fit
input is **not cut off**. DIP05 coil maximum is **7.5 V** (`part.yaml` limits),
so the relay coils are over-driven, and the excess is absorbed only by `D_TVS`
(SMBJ5.0A, V_BR 6.4–7.07 V) sinking up to the eFuse's ~1.7 A limit (R_ILM
1.2 kΩ, interpolated from the 487 Ω/1780 Ω table rows) — >10 W in an SMB
package, i.e. the TVS is sacrificed doing the eFuse's job. A 12 V adapter *is*
caught (1.565 V > 1.27 V). The brief §3.5 asked for an "OV cutoff"; what shipped
is an OV cutoff at nearly 2x the rail.

fix: `R_OVB` 15 kΩ → 26.7 kΩ (or R_OVT → 374 kΩ). One resistor.

### P1-6 The opto "dry contact" can only guarantee ~2 mA, against a stated ≤30 V/50 mA rating

evidence: `CONTACTOR_DRV` (SN74LVC1G11 output, VCC = 3V3) → `R_OPTOLED`
**330 Ω** → LTV-817S anode. SCES487I §5.5: V_OH ≥ 2.4 V at I_OH = −16 mA /
VCC = 3 V, ≥ VCC−0.1 at −100 µA; interpolating at ~6 mA gives V_OH ≈ 2.7 V worst
case, ≈3.15 V typical. LTV-817 V_F ≈ 1.2 V typ / 1.4 V max. So **I_F = 3.9 mA
worst case, 5.9 mA typical**. `part.yaml` limits: `ctr: "50-600% (TA1 bin)"` —
the TA1 reel is unbinned, so **CTR_min = 50 %**. Guaranteed I_C = 0.5 × 3.9 mA =
**1.95 mA** (2.9 mA at typical drive), before LED aging derates it further over
life.

consequence: the J_CONTACTOR output is silkscreened and specified as a
30 V/50 mA dry contact (brief §3, `part.yaml` gotcha). It can drive a
high-impedance PLC/SSR input; it **cannot** drive a contactor coil or anything
drawing more than ~2 mA, and at 2 mA the phototransistor is not well saturated.
This is a functional mis-rating on the board's primary de-energise actuator, so
it must be resolved before the appliance is connected.

fix: either drop `R_OPTOLED` to ~150 Ω (I_F ≈ 13 mA → ≥6.5 mA guaranteed) and
buy a CTR-binned part, or state plainly in the release that an external
interposing relay/SSR is mandatory and that the output is a ≤2 mA signal, not a
contact.

### P1-7 The isolated contactor loop shares a 1.25 mm-pitch connector with SELV logic

evidence: `J_ESTOP` (SM05B-GHS-TB, **1.25 mm pitch**): pin 1 = 3V3, pin 2 =
`ESTOP_RAW`, pin 3 = `CONTACTOR_C` (opto collector), pin 4 = `CONTACTOR_LOOP`,
pin 5 = GND. Pins 2 and 3 are adjacent. The LTV-817S is rated V_ISO = 5 kVrms
and its `part.yaml` layout note demands the full 9.53 mm body creepage be
preserved across the barrier — that barrier is then reduced to **1.25 mm** at
this connector, and to whatever the PCB gives between `CONTACTOR_C/E/LOOP` and
GND.

consequence: any contamination, condensation or wicking bridge between J_ESTOP
pins 2 and 3 puts contactor-loop potential directly onto `ESTOP_RAW` →
`U_SCHM.1` → destroys the E-stop sense input, and defeats the isolation the opto
exists to provide. This is a cooking appliance with a steam-carrying exhaust
path.

order-time mitigation (acceptable): declare in the release that the contactor
loop is **SELV, ≤30 V, and must never be bonded to mains or to any
mains-referenced controller common**, and conformal-coat the J_ESTOP area.
Proper fix: move the loop onto its own KF350-class terminal block (J_CONTACTOR
already is one) and put only the E-stop sense on J_ESTOP.

### P1-8 The switched sensor rails carry the I2C pull-ups, so a stuck-bus power-cycle clamps the bus low

evidence: `R_SDAA`/`R_SCLA` (2.2 kΩ) pull `SDA_A`/`SCL_A` to **`3V3_SW_A`**, not
3V3; likewise `R_SDAB`/`R_SCLB` to `3V3_SW_B`. `3V3_SW_A` is switched by `Q_SWA`
(AO3401A) whose gate `SWG_A` is driven from `RAIL_EN_A` = MCP23017 GPA0 with
`R_RAENAPD` 100 kΩ **pulldown** (default OFF). But `J_RH_AMBIENT` sits on the
*same* bus (`SDA_A`/`SCL_A`, pins 3/4) powered from a *different* rail,
`3V3_SW_RHA`.

consequence: (a) at power-on both buses have **no** pull-ups and are actively
pulled toward 0 V through 2 × 2.2 kΩ into a dead rail — 2.2 kΩ beats the modules'
10 kΩ, so the bus is stuck low until the host enables the rails; a bring-up trap.
(b) Power-cycling thermal head A to recover a stuck bus (brief §3 "switched
sensor rails ... for stuck-I2C power-cycling", C6) **kills the pull-ups for the
whole bus**, taking the ambient SHT45 down with it — the recovery mechanism
cannot work. (c) Cycling `3V3_SW_RHA` alone leaves the SHT45's SDA/SCL pins
pulled to a live rail while its VDD is 0, back-powering it through its ESD
diodes so it never actually resets — exactly failure C7.

fix: move the four bus pull-ups to the permanent 3V3 rail (they are then always
correct, and the brief's C7 "DNP if the module pullups are strong enough"
decision applies to a resistor you can actually depopulate).

### P2-1 Floating CMOS inputs with no actuator consequence

`PRESS_REQ` {U_SR1.7, U_ONESHOT.2} has **no pull at all**; `DECU_A/B/C` and
`DECD_A/B` float when the 595 is tri-stated (harmless — `R_DECUPD`/`R_DECDPD`
100 kΩ hold both G1 enables low, and the '238 drives all Y low when disabled);
`KEY_DATA`, `KEY_CLOCK`, `KEY_LATCH`, `ADC_CS_N`, `TC_CS_N`, `SPI_SCLK/MOSI/MISO`
float with the ribbon off. None can energise an actuator (see the hunt section).
The 595 `part.yaml` gotcha — *"OE_N high = outputs Hi-Z; ULN2803 inputs then held
off by their internal base network"* — is now **stale**: in v1.2 the 595 feeds
'238 and '221 CMOS inputs, which have no such network. Add 100 kΩ pulldowns on
`PRESS_REQ` and the five decoder address lines, and pulls on the four Pi control
lines and two chip selects.

### P2-2 100 kΩ default-state pulldowns are at the LVC datasheet leakage limit

SCES487I §5.5: `I_I = ±5 µA max` (V_I = 5.5 V or GND). `MCU_RELAY_ENABLE` drives
**two** LVC inputs (U_AND2.3 and U_OENAND.1): 2 × 5 µA × 100 kΩ = **1.0 V** vs
V_IL(max) = **0.8 V** at VCC = 3.3 V. Same arithmetic on `STOP_REQ` (U_STOPINV
has both inputs tied). Typical leakage is orders of magnitude lower so this will
work in practice, but the worst-case datasheet number does not close. 10 kΩ
restores 10x margin at 0.33 mA of host drive.

### P2-3 Comparator hysteresis is ≈3.9 mV (0.32 K), below the LM393's own offset spec

At the trip point the source impedance at `TH_CAM_A` is 10 kΩ ∥ 1.471 kΩ =
1.282 kΩ; `R_HYS1` = 1 MΩ and TEMP_OK swings ≈3.04 V, giving ΔV_node = 3.04 ×
1282/(10⁶+1282) = **3.90 mV**. Divider slope at the trip point is dV/dT =
−12.1 mV/K, so hysteresis = **0.32 K** — against an LM393 V_OS spec of ±5 mV
(SLCS005AH). Because `TEMP_OK` is in the fault-latch SET term (`U_FAULTAND.6`),
a single 1.3 µs dither edge latches the board off permanently until re-arm —
protective, but expect nuisance latching near the threshold, on a high-impedance
node the part.yaml itself flags for pickup. Also both 1 MΩ feedbacks land on a
shared output, so a channel-A trip drags channel B 0.32 K closer to tripping.
Drop R_HYS to ~150 kΩ for ~26 mV (≈2 K).

### P2-4 Relay pull-in headroom is ~0.36 V at a 5 % low supply

Coil 500 Ω ±10 %, **pull-in ≤3.5 V** (DIP05 `part.yaml`). Path drops at 5.00 V
in: polyfuse ≈30 mV + Q_REV 60 mΩ + eFuse R_ON 34 mΩ ≈ 70 mV total at 400 mA,
Q_COIL negligible → `5V_KEY_RELAY` ≈ 4.93 V; ULN2803A V_CE(sat) at 10 mA ≈
0.85 V (extrapolated from the SLRS049 table, which specifies 1.1 V max at
100 mA) → coil ≈ **4.08 V**, margin 0.58 V. At 4.75 V in: coil ≈ 3.86 V, margin
**0.36 V**. Below ≈4.4 V input the relays stop guaranteeing pull-in. Specify the
5 V SELV supply at ±5 % in the order README and measure `TP_5VKR` at G5.

### P2-5 EFUSE_FLT_N is pulled to 5 V into a 3.3 V expander input

`EFUSE_FLT_N` = {`U_EFUSE.6` (open-drain), `R_PG` 100 kΩ to **5V_PROTECTED**,
`U_EXP.1` GPB0, `TP_PGOOD`}. MCP23017 DS20001952C absolute maximum: *"Voltage on
all other pins with respect to VSS ... –0.6 V to (VDD + 0.6 V)"* = **3.9 V**. The
input clamp holds it at ~3.9 V drawing (5.0−3.9)/100 kΩ = **11 µA**, well inside
the ±20 mA I_IK rating, so no damage and the pin still reads a valid 1 — but it
is an abs-max exceedance relying on the protection diode, and it injects 11 µA
into 3V3. Move `R_PG` to 3V3.

### P2-6 KEY_LATCH_G produces a spurious RCLK edge at the end of every press

`U_LATCHG = AND(KEY_LATCH, PRESS_TIMED_N, 3V3)`. When the '221 pulse ends,
`PRESS_TIMED_N` rises; if the host left `KEY_LATCH` high, `KEY_LATCH_G` gets a
0→1 edge and the 595 **latches whatever is currently in the shift register** —
immediately, with the coil rail still up. The freeze (D10 item 7) is correct;
the un-freeze is not edge-safe. Host must drop `KEY_LATCH` low before or during
the press; make it a driver invariant and a G5 test. Related and already
documented in the '221 `part.yaml`: with `PRESS_REQ` still high, a rising
`OS_CLR_N` (STOP or door abort releasing) re-triggers one bounded ≈380 ms press.

### P2-7 The host has no fast, bus-independent way to drop the external contactor

`CONTACTOR_REQ` reaches `U_CAND2.6` only from MCP23017 GPA4 — an **I2C register
write**. `STOP_REQ` (GPIO26, direct) preempts the keypad but appears in neither
`U_CAND1` nor `U_CAND2`, so a hardware STOP leaves the contactor closed. If the
I2C bus is wedged (see P1-8, and the board ships explicit stuck-bus recovery
machinery, so this is anticipated), the only remaining host-controlled
de-energise is to stop petting the watchdog — 0.9–2.5 s and latching. Consider
ANDing `STOP_REQ_N` into `CONTACTOR_DRV`, or homing CONTACTOR_REQ on a spare
direct GPIO (J_PI pins 12/18/35 are free).

### P2-8 TEMP_OK's permissive level is produced passively, so a dead comparator reads "safe"

`TEMP_OK` is a wired-AND of two open-collector outputs with `R_TEMPOK` 10 kΩ to
3V3. If the LM393 dies, loses 5V_PROTECTED, or is simply not populated,
`TEMP_OK` is pulled **high = permissive**, silently. Inherent to open-collector,
but it means the over-temp inhibit has no self-test. The board can cross-check —
`TH_CAM_A`/`TH_CAM_B` also reach MCP3208 CH0/CH3 via `R_SER0`/`R_SER3` — so make
"host compares TEMP_OK (expander GPB4) against the ADC reading of CH0/CH3, and
refuses to arm on disagreement" a documented bring-up and runtime requirement.

### P2-9 Brief deviations worth recording

- `TH_ENCLOSURE` (ADC CH6) and `TH_SPARE` (CH7) have **no connector** — only
  `R_REF6`/`R_SER6` and a test pad. Brief §3 lists TH_ENCLOSURE as a required
  channel with a ≤50/55/65/75 °C limit; it can only be attached by soldering to
  `TP_ENCL`.
- No per-channel ESD on the eight thermistor inputs (brief §3 asks for it); ESD
  devices exist only on `DOOR_RAW`, `ESTOP_RAW`, `LC_DAT`, `LC_CLK`, `5V_IN`.
  `MODE_RAW`, `COIL_EN` and `KEY_RELAY_ALLOWED` leave the board on an external
  cable with **no** ESD device and no series resistance — and
  `KEY_RELAY_ALLOWED` is the AND-chain output, so a destroyed `U_AND3` output
  stuck high energises the coil rail (the mode switch is the only remaining
  channel, and it is closed during normal cooking).
- Series resistors on Pi lines: brief asks 22–100 R; present only on
  `LC_DAT`/`LC_CLK` (33 Ω).
- `R_KEY`/`R_STOP` are single 0 Ω 1206 parts, not the brief's
  0/22/47/100/220/470/1k solder-select field (TP_RKEY/TP_USEL/TP_DSEL do provide
  the decade-box access point).
- `SHIELD_DRAIN` is 0 Ω-bonded to GND via `R_SHIELD` — one of the brief's
  permitted options, but it is the hard-bond one.
- `K_STOP` is live in MANUAL (5V_STOP bypasses Q_COIL), whereas brief §3 says
  MANUAL physically disables relay power. This is deliberate per D10 item 5; the
  residual is that a buggy host can press STOP/CLEAR while a human operates the
  panel manually. Related: `K_STOP` is the **only** relay whose contact alone
  presses a key — the U/D+PRESS series topology means no single welded selector
  can ever press a key, which is a genuinely strong property, but a welded
  K_STOP or a shorted `Q_STOPDRV` holds U6–D1 down permanently and will look
  like a stuck key to the OEM controller.

### Things I checked and found correct

Worth stating so the next reviewer does not redo them: the '238 (active-HIGH) vs
'138 choice is right for the ULN interface and is verified against the D2804
function table; ULN2803 `COM` is on the **switched** rail (both devices, pin 10)
as the flyback clamp requires; `D_KSTOP` orientation is correct; the NAND fault

reverse-polarity orientation and `D_REVCLAMP` are correct; the MAX31856 front end

# ROUND 2 — re-verdict after R_WDPETPD 100 kΩ → 1 kΩ (verbatim)

## P0-1 IS CLOSED — and your 1k was RIGHT, my 100k brief was WRONG

I specified a 100k pull-down for WD_PET. You used 1k. The reviewer independently
derived that 1k is correct and 100k would NOT have worked, and I have checked the
arithmetic: TPS3823 WDI I_IL = 190 uA max (SLVS165O sec.6.5), V_IL = 0.3*VDD =
0.99 V at 3.3 V. R_max = 0.99 V / 190 uA = ~5.2 k. A 100k pull-down sits at
essentially VDD and never holds WDI low — my number would have left the P0 OPEN
while looking fixed. Your 1k gives 190 uA * 1k = 0.19 V, margin 0.80 V (81%).
Even 4.7k gives 0.893 V = only 97 mV margin (11%), too thin for a safety
supervisor. Keep 1k. Record in the commit body that 1k is derived from
I_IL*R < V_IL, not chosen by habit — this is exactly the kind of number that gets
"rounded up" later by someone economising on pull-down current.

## VERDICT: **ORDER** — conditional. Two mitigations must be MANDATORY order-document lines, not advisory notes.

The conditionality is the whole verdict. If these land as soft prose, the verdict
does not hold.

**P1-2 (door input is INERT — R_DOORPU pulls to 3V3, not GND).** MANDATORY
harness spec in ORDER_README and on the J_DOOR label: Form-B (magnet-opens) reed
wired J_DOOR.2 -> J_DOOR.3 (GND); do NOT wire to J_DOOR.1 (3V3); note J_DOOR.2
and .4 are the same net. G4 sign-off must DEMONSTRATE DOOR_OK = 1 door-closed, 0
door-open. README must state plainly that a broken or unplugged door cable reads
PERMISSIVE this revision — unlike every other safety input on the board. With the
naive pin2->GND harness K_PRESS can never fire and the board is simply
non-functional, so the harness spec decides between "inert" and "broken".

**P1-3 (open/unplugged camera thermistor reads COLD, defeating the hardware
over-temp inhibit).** MANDATORY host runtime check: cross-check TEMP_OK (expander
GPB4) against MCP3208 CH0/CH3 every sample; refuse to arm on disagreement or any
reading above the open-circuit bound. G4 sign-off must DEMONSTRATE that an
unplugged thermal head blocks arming. README must state the LM393 inhibit does
not detect an open sensor and that the OEM thermal cutoffs remain primary. The
reviewer flags this as the one to fix first in v1.3 because its mitigation is a
RUNTIME SOFTWARE requirement — structurally weaker than every other mitigation on
the list.

## NEW WORK THE FIX CREATED — bring-up order is now load-bearing

Before, the watchdog never fired, so nothing depended on sequencing. Now WDI sits
solidly low from power-on and the '3823 pulses RESET every ~1.6 s until the host
pets, and each pulse re-sets the fault latch via U_FAULTAND -> FAULT_SET_N. If
the driver pulses REARM_N before the heartbeat runs, the re-arm is undone within
2.5 s and the board looks intermittently broken. Document this MANDATORY order:
start GPIO17 heartbeat -> confirm TP_WDOK steady high for >2.5 s -> pulse
REARM_N -> then HOST_AUTH / MCU_RELAY_ENABLE. Also note TP_WDOK PULSES (not low)
throughout the ~20-30 s Pi boot, or someone will chase it as a fault.
Optional, your call: the '3823 triggers on the NEGATIVE edge with t_w(WDI) min
100 ns, so parking GPIO17 low and pulsing high briefly drops average pet current
from 1.65 mA to ~0.

## ONE INTERACTION TO WRITE AS A SINGLE CLAUSE

The P1-6 mitigation makes P1-7 worse. P1-6 requires an interposing relay/SSR on
J_CONTACTOR (the opto guarantees only ~2 mA, not the rated 30 V/50 mA — at 2 mA
the phototransistor is not saturated, so a directly-driven contactor can CHATTER
or partially engage rather than cleanly failing to pull in). But that relay's
coil supply (likely 12/24 V) then lands on J_ESTOP pins 3/4, 1.25 mm from
ESTOP_RAW and GND. Write them together: the contactor loop is SELV, <=30 V, never
bonded to mains or a mains-referenced common — EXPLICITLY INCLUDING the
interposing relay's own coil supply. Conformal-coat J_ESTOP. Record that the
LTV-817S 5 kVrms barrier is reduced to 1.25 mm at J_ESTOP pins 2/3, accepted only
under that SELV declaration.
