# Fresh-context pin review — pluto-rx2-8way-v2, 12 parts

## Scope and method

I did not design this board. For each part I derived the expected pinout from the
vendor's **pin-configuration figure** first — rendered from the PDF and read
visually — and only then opened the dossier's net column. The repo's own
`part.yaml` `pins:` block was not consulted before the derivation; where I quote
it below, it is as the artifact under test, never as a source.

## 1. U_SW — PE42482A-X, SP8T, QFN-24 4×4×0.85 with exposed pad

### 1a. Winding and mirror check (the check that exists because of the mirrored-footprint incident)

Derived from Figure 22 (p20), top view, pin-1 dot at the **top-left corner**:

- pins **1–6** run **DOWN the WEST side** (LS, RF2, GND, RF3, GND, RF4)
- pins **7–12** run **LEFT→RIGHT along the SOUTH side** (GND, VDD, V1, V2, V3, V4)
- pins **13–18** run **BOTTOM→TOP up the EAST side** (RF5, GND, RF6, GND, RF7, GND)

winding is **CCW (top view)** and its side column reads W×6 → S×6 → E×6 → N×6 in
exactly that order, with pad 1 at local (−1.90, −1.25) = west side, topmost.
**Not mirrored. PASS.**

Land-pattern cross-check against Figure 23 (p21) "RECOMMENDED LAND PATTERN":
datasheet 0.60 × 0.30 (×24), pitch 0.50 (×20), EP **2.75 × 2.75**, overall 4.40.
Board footprint: side pads 0.6 × 0.3 (rotated 0.3 × 0.6 on N/S as they must be),

2.75 × 2.75 ✓. **Geometry matches the vendor land pattern.**

### 1c. The select lines, decoded from Table 5 (p10) — read visually, not from the text layer

Table 5's column order is **LS, V4, V3, V2, V1** (left to right). With LS = 0:

| V4 V3 V2 V1 | port ON |
|---|---|
| 0 0 0 0 | RF1 |
| 0 1 0 0 | RF2 |
| 0 0 1 0 | RF3 |
| 0 1 1 0 | RF4 |
| 0 0 0 1 | RF5 |
| 0 1 0 1 | RF6 |
| 0 0 1 1 | RF7 |
| 0 1 1 1 | RF8 |

So the port index obeys **n − 1 = 4·V1 + 2·V2 + 1·V3**: **V1 is the MSB, V3 is
the LSB, and V4 is not a select bit at all** — Table 5 note 2 states that V4 = 1
with V3 = V2 = V1 = 0 terminates every port (all-isolated), i.e. V4 is an
isolate/mute control that must be held LOW throughout a sweep.

Board wiring, traced end to end:

`U_MCU pad 1 (GP0) → SEL_V1 → R_S1 47R → SW_V1 → U_SW pin 9 (V1, MSB)`
`U_MCU pad 2 (GP1) → SEL_V2 → R_S2 47R → SW_V2 → U_SW pin 10 (V2)`
`U_MCU pad 3 (GP2) → SEL_V3 → R_S3 47R → SW_V3 → U_SW pin 11 (V3, LSB)`
`U_MCU pad 4 (GP3) → SEL_V4 → R_S4 47R → SW_V4 → U_SW pin 12 (V4, isolate)`
each with R_PD1..R_PD4 = 10k to GND at the switch end.

**No transposition and no reversal in copper.** The V-index on the MCU side
matches the V-index on the switch side one-for-one. Divider level when driven
high: 3.3 × 10000/10047 = **3.285 V**, against the part's V_IH of 1.17 V —
comfortable. Power-on state with all four pull-downs = 0000 = **RF1 ON**, a
selected port rather than the muted state (V4 = 0). All correct.

**VERDICT U_SW: PASS** (25 of 25 electrical pads graded).

## 2. U_MCU — Waveshare RP2040-Zero module, 23 castellated pads

### 2a. Vendor numbering derived independently

From the Waveshare schematic "Pin Out" block, header **P1 (Header 23)**, PDF p1,
pin 1 → 23 reads: GPIO0, GPIO1, GPIO2, GPIO3, GPIO4, GPIO5, GPIO6, GPIO7,
GPIO8, GPIO9, GPIO10, GPIO11, GPIO12, GPIO13, GPIO14, GPIO15, **GPIO26, GPIO27,
GPIO28, GPIO29, 3V3, GND, VSYS**. (So the GPIO number tracks pad−1 for sixteen
consecutive pads, then jumps to GP26 — this is the divergence the numbering trap
lives on.)

From the vendor pinout figure (`RP2040-Zero-details-7.jpg`), with the USB-C at
the top of a top view, the physical order is:

- **RIGHT column, top → bottom (9 pads): GP0, GP1, GP2, GP3, GP4, GP5, GP6, GP7, GP8**
- **BOTTOM row, right → left (5 pads): GP9, GP10, GP11, GP12, GP13**
- **LEFT column, bottom → top (9 pads): GP14, GP15, GP26, GP27, GP28, GP29, 3V3, GND, 5V**

i.e. the numbering starts **top-right and winds CLOCKWISE in top view** — the
mirror of the CCW convention every IC uses, and therefore the exact place a
footprint author reflexively gets it backwards.

Footprint geometry (rotation undone, +y down = top view; USB edge is the −y edge,
identified by the fact that the 5-pad row sits at +y and there is no row at −y):

- pads 1–9 at x = **+8.70** (right), y = −10.16 → +10.16 → GP0..GP8 ✓
- pads 10–14 at y = **+11.45** (bottom), x = +5.08 → −5.08 → GP9..GP13 ✓
- pads 15–23 at x = **−8.70** (left), y = +10.16 → −10.16 → GP14, GP15, GP26..GP29, 3V3, GND, 5V ✓

Body 18 × 23.5 mm; column spacing 17.40 mm and bottom row at 11.45 mm are both
0.30 mm in from the respective 18.0 / 23.5 edges — consistent with edge
castellations. **Winding computed by the dossier: CW (top view). Matches the
vendor. Not mirrored. PASS.**

Schematic symbol pin names confirm the same map independently (pad 1 = GP0 …
pad 17 = GP26 … pad 21 = 3V3, 22 = GND, 23 = 5V), so the netlist, the footprint
and the vendor figure all agree — and they agree with the world, not just with
each other.

## 3. The ten SMA jacks — KH-SMA-KE-Z (J_ANT1..J_ANT8, J_RX1, J_RX2)

### 3a. Which pad is the centre pin — derived from the vendor drawing

Sheet 2/2 (PDF p2) of the Kinghelm KH-SMA-KE-Z drawing carries three views:

- **flange / rear view**: a 6.5 mm square flange with **4-SQ0.9** posts on a
  **5.08 × 5.08** square, and the coaxial centre pin at the **geometric centre**.
- **PCB layout inset ("PCB示意图")**: **5-Ø1.4** holes — four on a 5.08 × 5.08
  square, and **one in the middle**.
- side view: 13.5 overall, 8 mm 1/4-36UNEF Ø6.2 thread, 0.9 posts.

**The vendor drawing assigns no pin numbers at all.** So the mapping cannot be
cited to a numbered vendor pin; it is fixed instead by geometry, and that
geometry is unambiguous: the four 5.08-square holes take the flange ground posts
(they are mechanically the flange legs and can be nothing else), and the single
**centre hole is the coaxial signal pin**. Any footprint that puts RF on a corner
hole is dead on arrival, and would be visible as a 2.54/2.54 offset.

Board footprint `SMA_Vertical_5.08sq_D1.4`, identical on all ten jacks:
pad 1 at local **(0.00, 0.00)** — the centre — drill 1.4 mm, pad 1.9 mm
(0.25 mm annular ring); pads 2–5 at **(±2.54, ±2.54)** = the 5.08 mm square,
same drill. Matches the inset exactly. **PASS on geometry for all ten.**

## QUESTIONS and notes (none of these block the order)

**Q1 — `J_ANT8` is a refdes that lies about its function (P2, build/silk hazard,
not an electrical defect).** J_ANT8's centre pin is on RX1_MAIN, hard-wired to
J_RX1 and only resistively tapped into the switch. Anyone who reads eight jacks
named J_ANT1..J_ANT8 will expect all eight to be switched to RX2, and seven of
them are. The intent is stated plainly in `01_docs/ARCHITECTURE.md` §1–2, so it
is a decision, not a slip — but the *board itself* carries only the refdes. Worth
a silk legend ("RX1 ANT") on the next revision so the board teaches its own
topology; nothing to fix before ordering.

**Q2 — the V1-is-MSB obligation now sits entirely in unwritten firmware (P2).**
The copper is right: GP0→V1(MSB), GP1→V2, GP2→V3(LSB), GP3→V4(isolate). But
`05_firmware/` contains only `contracts.md` — there is no code yet. The PIO
sequencer must encode port n as `V1V2V3 = binary(n−1)` with **V1 weighted 4**,
and must hold **V4 low** for the whole sweep (V4=1 with V1..V3=0 is the
all-ports-terminated state, Table 5 note 2, p10, which silently mutes RX2). A
firmware author who assumes the conventional V1=LSB gets a sweep order of
1,5,3,7,2,6,4,8 — which an angle-of-arrival solver absorbs as a permuted/rotated
array rather than as an error. This is exactly the failure the pin review is
meant to catch, and on this board it has been pushed one layer up into software.

**Q3 — no DC blocks on any RF port; this is permitted, and it is an operating
constraint on the user.** Table 8 note 1 (p20): RF pins 2, 4, 6, 13, 15, 17, 19,
22, 24 "must be at 0 VDC … do not require DC blocking capacitors … if the 0 VDC
requirement is met." Nothing on this board applies DC to any RF net, so the
condition holds as built. But every antenna jack is DC-coupled straight to a
switch pin: connecting a bias-tee-powered or DC-fed active antenna to
J_ANT1..J_ANT7 (or feeding DC back in from the SDR on J_RX1/J_RX2) puts that DC
directly on the part. Stating it here so it lands in the release notes rather
than in a failure report.

**Q4 — pin 20 (NC) tied to GND is explicitly sanctioned**, Table 8 note 2 (p20):
"can be connected to GND or left not connected externally." I checked this
specifically because "NC pins carry no net" is a standing rule and this board
breaks it; the datasheet is the authority and it permits the tie.

**Q5 — the RX1 pickoff loads the RX1 through-path.** R_T1 + R_T2 = 440 Ω from
RX1_MAIN into RF8's 50 Ω port is a ~490 Ω shunt across the RX1 line. That is a
design trade (documented in `01_docs/DETAIL_DESIGN.md`: −20.26 dB tap,
0.432 dB insertion), not a pin error, and I did not re-derive it — it is outside
this review's remit. Flagged only so it is not mistaken for something this review
graded.

## Coverage

**98 of 98 electrical pads graded (100%).**

- U_SW (PE42482A-X): **25 / 25** — 24 numbered pins + pad 25 (EP).
- U_MCU (RP2040-Zero): **23 / 23**.
- J_ANT1..J_ANT8, J_RX1, J_RX2 (KH-SMA-KE-Z): **50 / 50** — ten jacks × 5 pads.

**Pads NOT graded, named and explained: 9.** They are the nine unnumbered
0.75 × 0.75 mm pads inside U_SW's exposed pad, at footprint-local (x, y) for
x ∈ {−0.95, 0, +0.95} × y ∈ {−0.95, 0, +0.95} — a 3 × 3 grid on 0.95 mm pitch.
I confirmed by layer inspection that
**all nine are `F.Paste` only** — no copper, no mask, no net, no pin number.
They are the EP's stencil subdivision (9 × 0.5625 mm² = 5.06 mm² over a
7.5625 mm² EP, ≈ 67 % paste coverage), not electrical pads, so there is no pin
for them to be right or wrong about. Every pad on this board that can carry a net
was graded.

**Two denominators worth stating honestly:**

1. The KH-SMA-KE-Z vendor drawing **assigns no pin numbers**, so for the 50 SMA
   pads I could not check "board pad N vs vendor pin N". I checked the stronger
   thing available — pad *position* against the vendor's own PCB hole inset — and
   the centre/corner distinction is unambiguous. Recorded as PASS on geometry.
2. The RP2040-Zero has **no true datasheet** in `02_parts/` (`- datasheet: (none)`
   in the dossier, and the dossier's `part.yaml` function column reads
   "(not in yaml)" for all 23 pads). I graded it against the vendor's own
   schematic PDF and vendor pinout figure instead, both of which are present in
   `02_parts/RP2040-Zero/`. The map they give is complete and self-consistent, so
   coverage is not reduced — but the *dossier* for this part shipped with an
   empty function column and no verification note, which is a gap in the audit
   input rather than in the board. Worth closing before the next pin review, or
   the next reviewer has nothing to compare and may not notice.
